# Пополнения через Laveshka / Lave Pay

Реализованы два направления **приёма оплаты**, не выводы:

* «Лавэшка»: обычный USD-счёт `/invoices`, ссылка на экран Laveshka. На нём покупатель выбирает доступный способ, включая СБП у верифицированного мерчанта.
* «СБП»: список провайдеров `/buy/rate`, в том числе провайдеры с оплатой пополнением телефона. Покупка USDT пополняет баланс мерчанта; только подтверждённая покупка начисляет Stars пользователю.

## Настройка

В приватный `conf.json` добавьте два поля (значения получите в консоли мерчанта):

```json
{
  "LAVESHKA_API_KEY": "",
  "LAVESHKA_WEBHOOK_SECRET": ""
}
```

Это дополнение к существующему конфигу, **не замена всего файла**. Права файла — `0600`. Не коммитьте ключи и не отправляйте их в чат. Перезапустите сервер после изменения.

В консоли Lave Pay настройте URL **`https://ВАШ-ДОМЕН/laveshka`** и скопируйте секрет подписи `whsec_…` в `LAVESHKA_WEBHOOK_SECRET`. API-ключ имеет вид `LAVE-<merchant_id>-<secret>`. Переключатель выплат для этих функций не требуется. Кнопкой «Тест» проверьте доставку `webhook.test`. Домен должен проксировать POST `/laveshka` до `server.py` без редиректов и изменения тела.

Без обоих значений способы оплаты отключены. Нужен сетевой доступ сервера к `https://laveshka.io/merchant/v1`. В этой среде реальные запросы провайдеру не выполнялись: интеграционные тесты используют подменённый API.

## Курс и комиссии

Курс прежний: **1 Stars = $0.022**. Сумма USD округляется вверх до цента. Пользователь получает ровно выбранное количество Stars, комиссию провайдера несёт мерчант. Локальный минимум — 5 Stars ($0.11); провайдер покупки USDT может потребовать существенно больше. Его курс и диапазон показаны при выборе; окончательные ограничения проверяет API. При изменении курса выше сохранённого `max_rate` операция не отправляется по более дорогому курсу.

## Подтверждение и восстановление

* Подпись: HMAC-SHA256 по **сырому телу**, `timestamp + '.' + body`, секрет вебхука. Принимается временное окно ±300 секунд, проверяется merchant_id.
* Проверяются ID объекта, локальный заказ / idempotency_key, валюта и сумма. Для покупки дополнительно сверяются способ и провайдер.
* Начисление только по `invoice.status=paid` либо `buy_order.status=completed`. `pending`, `processing`, `awaiting_payment`, `overdue`, `cancelled` денег не начисляют. Поздний `completed` после `cancelled` принимается.
* Баланс, реферальная комиссия, статус и журнал события сохраняются одной SQLite-транзакцией. Уникальный источник начисления не позволяет повторно пополнить баланс при вебхуке и параллельной проверке.
* Запрос и ключ сохраняются **до** сетевого вызова. После потерянного ответа используется ровно тот же запрос и ключ — не новая покупка. Существующие объекты проверяются через GET.
* Фоновая сверка работает без открытого браузера: каждые 30 секунд до 20 неоплаченных заявок, по очереди. Большая очередь увеличивает интервал проверки конкретной заявки. Вебхуки обрабатываются сразу, 2xx возвращается после сохранения транзакции.
* Заявка с неподтверждённым ответом остаётся `creating`: это не доказательство оплаты или отказа. При длительном ожидании проверьте API-ключ, лимиты и журнал Lave Pay; не создавайте повторную покупку вручную.
* Старые/отменённые заявки остаются доступными для сверки и позднего подтверждения. Обычный неоплаченный счёт можно отменить кнопкой интерфейса; результат подтверждается провайдером. Покупка с выданным номером не отменяется. Автоматических возвратов и трат с баланса мерчанта нет.

Данные: `webapp_deposits`, `webapp_lave_orders` (неизменяемый запрос и последний объект API), `webapp_payment_events`, стандартный журнал баланса и рефералов.

## Телефон

На экране показываются номер, страна, оператор, сумма рублей и время. Пользователь должен проверить страну в банковском приложении, внести точную сумму **одним платежом** и до срока. После срока реквизиты не показываются. После `overdue` явно запрещается новая оплата, но поздний платёж ещё может зачислиться. Прямое получение реквизитов СБП в обход экрана Laveshka для обычных счетов не используется.

### Если ссылка на оплату не появляется

Сервер сохраняет последнюю безопасную ошибку создания/проверки в `webapp_lave_errors`; `create` и `status` возвращают её в `creationError`. Интерфейс показывает причину и ID сохранённой заявки вместо бесконечного индикатора. HTTP-код и известная категория отказа API доступны без вывода ключей или сырого ответа провайдера. Например, `HTTP 401, unauthorized` означает, что нужно проверить ключ мерчанта; `validation_error` — параметры/лимиты. После успешной проверки ошибка удаляется и появляется кнопка оплаты. В журнал пишутся только ID заявки, статус и безопасный код ошибки.

При неясном результате не создавайте новый платёж: сверка продолжает использовать сохранённый ключ. Наличие диагностической ошибки не доказывает, что провайдер не успел создать счёт.
