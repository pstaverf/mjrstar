# Оптимизация и исправления — 7 ноября 2026

## Что изменено

### Сервер / SQLite

- Список поддержки: вместо двух дополнительных SQL-запросов на каждый тикет — один запрос с индексированными подзапросами плюс один запрос общих счётчиков. 200 тикетов: **401 → 2 SELECT**.
- `/api/support/unread` больше не строит полный список тикетов: счётчики читаются одним запросом. Счётчики учитывают все обращения, а не только 200 отображённых.
- Вложения пачки сообщений читаются одним SQL-запросом вместо отдельного запроса для каждого сообщения. Добавлены индексы по сообщениям, автору/удалению и вложениям.
- Crash/Roulette не выполняют UPDATE JSON неизменившегося раунда на каждом тике. Пустая очередь не удаляется повторно. Частота игрового цикла 200 ms, формулы результатов и моменты выплат **не менялись**.
- Успешная проверка initData повторно используется только внутри одного HTTP-запроса, между middleware и обработчиком. Ключ включает исходную подписанную строку; разные запросы и пользователи не делят этот кеш. Проверки срока и чужого UID сохранены.
- WAL, транзакции, общая блокировка SQLite, DB_PATH и идемпотентность платежей/ставок не менялись. Параллельные writer-процессы и Redis не добавлялись.

### WebSocket / клиент

- Общие публичные фазы игр кешируются на 500 ms и переиспользуются соединениями. Поиск текущих комнат делает восемь индексированных обращений к последнему раунду вместо коррелированного прохода по каждой записи всей истории.
- **Балансы не кешируются**: каждый снимок читает свой баланс и ревизию доступных пользователю тикетов заново.
- Неизменившийся баланс не вызывает повторный обход DOM и обновление элементов при каждом событии WebSocket.
- Исправлена гонка лимита WebSocket: ожидающие Upgrade подключения учитываются до завершения handshake.
- HTTP polling остаётся резервом, денежные команды через WebSocket не принимаются.

### Раздача статики

Новый модуль `static_assets.py` подключён к существующему разрешённому списку публичных файлов. HTML/JS/CSS при поддержке gzip сжимаются в worker thread, а результат сохраняется в `.cache/http-static`. Холодные одновременные запросы одного файла объединяются в одну задачу сжатия. Тёплый кеш не требует повторного сжатия или worker thread.

Ключ варианта включает путь, размер и mtime исходника: замена файла не должна оставлять прежнюю gzip-копию. Сохраняются `Vary: Accept-Encoding`, ETag/304 и корректный Content-Type. Запросы Range получают обычный файл. При недоступности записи кеша раздача продолжает работать без сжатия. API, база, Python-файлы и платёжные секреты в этот кеш **не попадают**.

Важно: на вашем домене Cloudflare уже показывал `Content-Encoding: gzip`. Поэтому отношение исходного размера к gzip **не доказывает дополнительное ускорение относительно прежней загрузки через Cloudflare**. Оптимизация обеспечивает сжатие на origin и переиспользование готового результата; реальный эффект зависит от CDN и сети. Сжатие не уменьшает объём распакованного JS и не заменяет будущий code-splitting.

## Найденные и исправленные баги

1. Удалённые сообщения поддержки продолжали увеличивать unread — теперь исключены.
2. Удалённые сообщения после повторного открытия создавали пустые пузырьки — теперь пропускаются, но курсор сообщений продвигается.
3. В интерфейсе администратора свои ответы ошибочно считались входящими — направление уведомлений определяется владельцем сообщения.
4. Слишком большой клиентский `after` мог пометить будущие сообщения как прочитанные — сервер учитывает только реально доставленные ID.
5. Ответ чтения тикета мог содержать старый unread после обновления отметки чтения — используется обновлённая отметка.
6. Общий счётчик поддержки обрезался первой страницей в 200 тикетов — теперь считается по всем доступным обращениям.
7. Конкурентные холодные запросы могли повторять сжатие одного большого файла — объединены; отмена одного запроса не отменяет общую задачу.

## Локальные замеры

Фактические результаты: `PERFORMANCE_RESULTS.json`. Повтор:

```bash
PYTHONDONTWRITEBYTECODE=1 python tools/benchmark_runtime.py
```

Скрипт создаёт **временную тестовую базу**, не открывает production `bot.db`, не делает реальных Telegram/платёжных запросов. Сравнение поддержки выполняется пять раз: прежний шаблон N+1 и текущая сборка снимка с одинаковыми 200 тестовыми тикетами. Это микробенчмарк чтения, не HTTP-нагрузка и не показатель ускорения всего приложения.

Последний замер в sandbox:

| Проверка | До / исходник | После |
|---|---:|---:|
| Поддержка, SELECT на 200 тикетов | 401 | 2 |
| Поддержка, медиана локальной сборки | 112,059 ms | 2,235 ms |
| 64 последовательных WS-снимка | 256 запросов по прежней схеме (расчёт) | 130 SELECT, 34,273 ms (замер) |
| `app.js`, исходник → gzip | 3 221 627 B | 954 380 B |
| `styles.css`, исходник → gzip | 519 462 B | 89 448 B |
| `app_shell.html`, исходник → gzip | 167 794 B | 26 093 B |

64 WS-снимка — последовательная симуляция, не 64 полноценных клиента под нагрузкой. Замеры времени меняются от машины и нагрузки. Не заявляется конкретный production RPS, FPS или время загрузки Telegram WebView.

## Установка и проверки

Обязательно загрузить новый **`static_assets.py`** вместе с обновлёнными `main.py`, `live_games.py`, `support_backend.py`, `realtime_backend.py`, `app.js`, `support.js`, `index.html`, `sw.js` и остальным согласованным комплектом. Без нового модуля импорт `main.py` не запустится. Перезапустить существующий backend. При необходимости очистить кеш CDN для HTML/JS/CSS; не разворачивать старый `or.zip`.

Текущая версия ресурсов: `majorstars-performance-20261107-6`, Service Worker: `mjrstar-static-v30`. Индексы создаются автоматически при старте. При большой базе первый запуск с добавлением индексов может занять время — сначала согласованный backup SQLite. `.gitignore` исключает runtime-кеши и рабочую базу из случайного коммита.

Сервер должен иметь право создавать `.cache/http-static` для кеширования сжатых файлов; без этого сохранится обычная раздача. Старые варианты после нескольких обновлений можно удалить из **этой кеш-папки**, они восстановятся автоматически. **Не удалять `bot.db`, `bot.db-wal` и `bot.db-shm`.**

152 Python-теста и семь JS-наборов проходят, включая игровые выплаты/откаты, поддержку, безопасность WebSocket, gzip/ETag/Range/обновление исходника/одновременные запросы и постоянное количество SQL-запросов. Новые проверки не используют реальные платежи и Telegram броски. Production-сервер, его Nginx/Cloudflare, фактические сетевые задержки и браузерный E2E в этом сеансе не проверялись. Изменения локальные; автоматического deploy, commit или push нет.
